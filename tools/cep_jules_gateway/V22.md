# CEP Jules Gateway v2.2 — Reference Transport, Reconciliation, and Continuity

Status: active reference/mutation-canary infrastructure; this layer does not grant project acceptance, release, deployment, publication, or product-scope authority.

## Why v2.2 exists

v2.2 closes four transport/reconciliation blockers without turning GitHub transport into an authority source:

1. Mutation dispatch is reference-only. It accepts bounded public-safe control metadata and an opaque `drive:<file_id>` + SHA-256 instruction identity, never arbitrary private task bodies.
2. Mutation/reconciliation dispatch is restricted to the repository owner and `refs/heads/main`, with the gate repeated inside the reusable worker.
3. Unknown provider write outcomes have a read-only reconciliation path with `RECONCILED_APPLIED`, `RECONCILED_NOT_APPLIED`, or `RECONCILIATION_INCONCLUSIVE` outcomes.
4. `send_message` success requires a new exact `userMessaged.userMessage` activity matching the bridge-message digest. A session `updateTime` change alone is not success evidence.

## Current Controller topology

The v2.2 contract and dispatch UI use the same current topology as the rest of the packaged Gateway:

- `A -> W01`
- `B -> W02`
- `C -> W03`
- `D -> W04`
- `E -> W05`
- Parent may route `PARENT`, individual `W01..W05`, and the retained legacy aggregate fallbacks `W01_W02` / `W03_W04`.

Legacy aggregate routes are Parent-only. This is structural transport validation; Drive remains the authority owner.

## Existing Jules session continuity

The transition is a control/transport migration, not a Jules-session migration.

- Existing Controller sessions retain their exact Jules `session_id`.
- Existing plan/message/activity/changeSet/Bash/media history remains in the same provider session.
- Existing Git branches, commits, candidate SHAs, PRs, and lane evidence are not recreated or rewritten.
- The first v2.2 mutation of a pre-existing session adopts it by persisting a local binding marker for exact `session_id + logical_task_id + write_domain`. No Jules write is performed merely to bind an old session.
- Different sessions remain parallel. Only the same request identity and same mutation effect/session serialize.
- During coexistence, do not mutate one Jules session concurrently through independent legacy and v2.2 mutation paths.

## Public-safe reference bridge

For `create_session` and `send_message`, v2.2 constructs a short deterministic Jules message containing only bounded routing metadata, instruction action, opaque Drive reference, exact instruction digest, effect identity, and optional bounded authority references.

The bridge tells Jules to retrieve and verify the governed instruction through the established authority/source path and to stop if inaccessible or mismatched. GitHub transport does not carry the private/full task body.

## Mutation evidence

`create_session` verifies the returned/read-back session against deterministic correlation identity, source/starting branch where exposed, and post-state rather than treating a write call alone as success.

`send_message` captures the bounded pre-activity identity set, sends exactly once, then requires one new `userMessaged` activity whose message hashes to the exact bridge digest.

`approve_plan` retains the exact provider plan identity guard, including provider identity digest, stable `Plan.id`, activity identity/time, session update identity, and matching new `planApproved.planId` after the single approval call.

No mutation has an automatic retry. HTTP 429/5xx/transport ambiguity/inconclusive post-read becomes `UNKNOWN_WRITE_OUTCOME` and routes to reconciliation.

## Reconciliation

Reconciliation is provider-read-only and runs under the same effect concurrency key as the original mutation.

- Create: exact deterministic correlation evidence proves APPLIED. A complete settled session listing without a correlated session may resolve NOT_APPLIED only under the documented bounded assumptions; provider consistency limitations remain explicit.
- Send: exact matching `userMessaged.userMessage` proves APPLIED. A complete settled activity read with no message plus unchanged session identity may resolve NOT_APPLIED; otherwise it remains INCONCLUSIVE.
- Approve: exact matching `planApproved.planId` proves APPLIED. Absence remains conservatively INCONCLUSIVE; v2.2 never blind re-approves.

Create-effect resolution and any reconciled session binding are persisted before terminal request resolution so crash recovery remains fail-closed.

## Provider/read improvements shared with v2.2

The common `JulesClient` now uses response-safe activity collection semantics, bounded GET-only page-size adaptation for provider responses exceeding the transport limit, and optional `createTime`/page-token read primitives. These improve long-session lifecycle reads without weakening mutation safety.

Inspect evidence can also preserve bounded media artifacts as digest-bound files instead of silently ignoring them.

## Remaining provider limitations

Jules `approvePlan` remains session-scoped and exposes no atomic plan-revision conditional token. v2.2 therefore still documents the narrow provider-level TOCTOU between the final exact read and POST; exact post-write `planApproved.planId` evidence is required before VERIFIED.

Provider list consistency and long-term page-token durability are not promoted into guarantees the API does not explicitly provide. Durable cache/checkpoint semantics require separate evidence before cutover.
