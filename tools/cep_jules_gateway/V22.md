# CEP Jules Gateway v2.2 — Reference Transport, Reconciliation, and Continuity

Status: shadow/canary infrastructure. This layer does not grant project acceptance, release, deployment, or product-scope authority.

## Why v2.2 exists

v2.2 closes four Parent-review blockers without replacing the existing read-only/v1 transports:

1. GitHub mutation dispatch is reference-only. It accepts bounded public-safe control metadata and an opaque `drive:<file_id>` + SHA-256 instruction identity, never arbitrary task prompt/title bodies.
2. Every mutation/reconciliation dispatch is restricted to the repository owner and `refs/heads/main`, with the gate repeated inside the reusable worker.
3. Unknown provider write outcomes have a real read-only reconciliation path with `RECONCILED_APPLIED`, `RECONCILED_NOT_APPLIED`, or `RECONCILIATION_INCONCLUSIVE` outcomes.
4. `send_message` success requires a new exact `userMessaged.userMessage` activity matching the bridge-message digest. A session `updateTime` change alone is not success evidence.

## Existing Jules session continuity

The transition is a control/transport migration, not a Jules-session migration.

- Existing A/B/C sessions retain their exact Jules `session_id`.
- Existing plan/message/activity/changeSet/Bash history remains in the same provider session.
- Existing Git branches, commits, candidate SHAs, PRs, and lane evidence are not recreated or rewritten.
- The first v2.2 mutation of a pre-existing session adopts it by persisting one local binding marker for the exact `session_id + logical_task_id + write_domain`. No Jules write is performed merely to adopt/bind an old session.
- Different sessions remain parallel. Only the same request identity and the same mutation effect/session serialize.
- During coexistence, do not mutate the same Jules session through v1 and v2.2 concurrently. v1 remains fallback until separate retirement is justified by live evidence.

## Public-safe reference bridge

For `create_session` and `send_message`, v2.2 constructs a short deterministic Jules message containing only bounded routing metadata:

- request/logical-task/write-domain identities;
- Controller/lane;
- bounded instruction action;
- opaque Drive instruction reference;
- exact instruction SHA-256;
- effect identity;
- optional bounded authority references.

The bridge tells Jules to retrieve and verify the referenced governed instruction through the established CEP authority/source path and to stop if inaccessible or mismatched. GitHub transport does not carry the private/full task body.

## Mutation evidence

`create_session` verifies the returned/read-back session against deterministic correlation title + exact bridge prompt digest and source/starting branch when Jules exposes those fields.

`send_message` captures the complete bounded pre-activity identity set, sends exactly once, then requires one new `userMessaged` activity whose `userMessage` hashes to the exact bridge message digest.

`approve_plan` retains the exact provider plan identity guard, including provider identity digest, stable `Plan.id`, activity identity/time, session update identity, and matching new `planApproved.planId` after the single approval call.

No mutation has an automatic retry. HTTP 429/5xx/transport ambiguity/inconclusive post-read becomes `UNKNOWN_WRITE_OUTCOME` and routes to reconciliation.

## Reconciliation

Reconciliation is provider-read-only and runs under the same effect concurrency key as the original mutation.

- Create: exact deterministic title + bridge prompt digest (+ source/branch when exposed) proves APPLIED. A complete settled session listing without a correlated session can resolve NOT_APPLIED, but Jules documentation does not explicitly promise immediate list consistency; that residual provider-consistency limitation is surfaced in the receipt rather than hidden.
- Send: exact matching `userMessaged.userMessage` proves APPLIED. A complete settled activity read with no message plus unchanged session update identity can resolve NOT_APPLIED; otherwise it remains INCONCLUSIVE.
- Approve: exact matching `planApproved.planId` proves APPLIED. Absence remains conservatively INCONCLUSIVE; v2.2 never blind re-approves.

Create-effect resolution and any reconciled session binding are persisted before the terminal request-resolution artifact, so crash recovery remains fail-closed.

## Remaining provider limitation

Jules `approvePlan` remains session-scoped and exposes no atomic plan-revision conditional token. v2.2 therefore still documents the narrow provider-level TOCTOU between the final exact read and POST; exact post-write `planApproved.planId` evidence is required before VERIFIED.

Likewise, Jules documents ListSessions pagination but does not explicitly document a strong-consistency guarantee immediately after an ambiguous create. Reconciliation therefore records that residual limitation whenever NOT_APPLIED is inferred after the configured settle window.
