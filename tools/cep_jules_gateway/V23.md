# CEP Jules Gateway v2.3 — Trusted Candidate Publication

Status: active trusted candidate-publication infrastructure on `main`; publication is transport evidence only and is not product acceptance.

## Objective

v2.3 removes Jules sandbox Git transport/credential limitations from the product-lane publication path without placing GitHub credentials inside Jules. Jules remains an implementation/review workspace; GitHub Actions is the trusted candidate publisher.

Flow:

`Controller reviewed Jules changeSet -> v2.3 publication preflight -> exact patch apply -> normal non-force branch push -> remote SHA readback`

## Security boundary

- Jules receives no GitHub PAT, SSH key, or repository write credential.
- The publisher uses the repository-scoped ephemeral `GITHUB_TOKEN` only inside GitHub Actions.
- Direct workflow dispatch is repository-owner-only and must originate from `refs/heads/main`.
- The optional issue bridge is owner-originated: only an owner-authored `[CEP-V23-PUBLISH]` issue can trigger it, and only `github-actions[bot]` may enter the publisher's bridge-provenance path.
- For bridged dispatches, the publisher independently re-fetches the exact issue and verifies repository, owner association, non-PR issue identity, title prefix, exact governed JSON body, and equality between body fields and workflow inputs. Bridge comments are not publication authority.
- Publication can target only existing isolated candidate/work branches permitted by the publisher contract. `main`, `master`, release namespaces, Gateway/control source, secrets/runtime/vendor paths, symlinks, gitlinks/submodules, binary patches, and high-confidence credential material remain fail-closed.
- Publication is candidate movement only. It never merges, releases, deploys, or changes acceptance authority.

## Exact review binding

Before any Git write, v2.3 re-reads Jules and requires reviewed evidence to match exactly, including:

- numeric `session_id`;
- quiescent allowed session state;
- exact session `updateTime`;
- exact GitHub repository source;
- exact latest unique changeSet activity;
- exact `baseCommitId`, matching the expected remote branch SHA;
- exact reviewed unidiff SHA-256;
- exact canonical changed-path SHA-256.

Any drift fails closed. An `IN_PROGRESS` session cannot publish.

The common activity reader now tolerates only one additional unambiguous terminal form: a successful object with no `activities` field and no continuation token is treated as an empty terminal page. Missing activities with continuation, wrong types, malformed identities, repeated tokens, incomplete scans, or other ambiguity still fail closed.

For read-only activity collection only, `PROVIDER_RESPONSE_TOO_LARGE` may trigger bounded `pageSize` reduction. Mutation retry behavior is unchanged.

## Parallelism and collision control

Concurrency is keyed by target branch, not globally. Independent A–E branch publications can proceed in parallel while publications to the same branch serialize. The provider session itself remains governed by one-writer-per-write-domain rules.

The current structural Controller mapping is `A=W01`, `B=W02`, `C=W03`, `D=W04`, `E=W05`; Parent retains explicitly supported individual and legacy aggregate routing. The shared tests guard this mapping across publication, v2 envelope, and v2.2 transport contracts.

## Publication and idempotency

The workflow first reads the remote branch and requires the exact expected SHA. It applies the exact reviewed patch to that SHA, commits with publication identity trailers, and performs a normal non-force push.

After push, the workflow reads the authoritative remote ref. A push command failure is not blindly retried: if readback equals the local candidate SHA the outcome can be reconciled as published; otherwise the workflow fails.

A repeated request can resolve `ALREADY_PUBLISHED` only when the current branch head is exactly one commit above the expected base and contains matching publication identity. Other remote movement is drift and fails closed.

## Issue-driven publication bridge

Controllers and Parent chats can trigger the publisher by opening an owner-authored issue whose title begins exactly with `[CEP-V23-PUBLISH]` and whose body contains the governed packet fields required by the current workflow, including Controller/lane, logical task/write domain, exact session identity/state/update time, target branch/base SHA, reviewed patch digest, and changed-path digest.

The bridge performs no Git write itself. It records dispatch intent and invokes the downstream publisher, which independently verifies issue provenance before publication work begins.

Bridge dispatch acceptance is not candidate acceptance, freeze, merge, release, or deploy evidence.

## Long-session reliability

The shared `JulesClient` preserves hard read budgets while supporting:

- terminal empty-object handling only when continuation is absent;
- bounded GET-only page-size fallback under the transport response-size condition;
- opaque pagination continuation metadata;
- optional provider `createTime` filtering for delta-style scans.

The W04-shaped regression suite exercises publication preflight through the real `JulesClient` across 550 activity rows plus an empty terminal page, as well as response-size fallback. Hosted tests remain synthetic provider simulations; they are not live Jules acceptance evidence.

## Performance intent

The publisher intentionally does not rerun the product's full test matrix. Product validation belongs to writer/Controller review and later PR/CI gates. Candidate publication performs identity, scope, patch-application, Git, and postcondition checks, keeping transport bounded while preserving fail-closed controls.
