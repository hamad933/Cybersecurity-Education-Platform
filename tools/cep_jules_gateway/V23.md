# CEP Jules Gateway v2.3 — Trusted Candidate Publication

Status: candidate infrastructure until reviewed and merged. Live publication is not claimed by this document.

## Objective

v2.3 removes Jules sandbox Git transport/credential limitations from the product-lane publication path without placing GitHub credentials inside Jules. Jules remains the implementation workspace; GitHub Actions becomes the trusted candidate publisher.

Flow:

`Controller reviewed Jules changeSet -> v2.3 publication preflight -> exact patch apply -> normal non-force branch push -> remote SHA readback`

## Security boundary

- Jules receives no GitHub PAT, SSH key, or repository write credential.
- The publisher uses the repository-scoped ephemeral `GITHUB_TOKEN` only inside GitHub Actions.
- Dispatch is repository-owner-only and must originate from `refs/heads/main`.
- Publication can target only existing isolated `work/`, `fix/`, `checkpoint/`, or `candidate/` branches. `main`, `master`, release/ref namespaces, workflow files, Gateway source, `.env`, vendor, node_modules, symlinks, gitlinks/submodules, binary patches, and high-confidence credential material are rejected.
- Publication is candidate movement only. It never opens/merges a PR, releases, deploys, or changes acceptance authority.

## Exact review binding

Before any Git write, v2.3 re-reads Jules and requires all of the following to match the Controller-reviewed evidence exactly:

- existing numeric `session_id`;
- a quiescent `COMPLETED` or `AWAITING_USER_FEEDBACK` session state;
- exact session `updateTime`;
- exact GitHub repository source;
- exact latest unique changeSet activity;
- exact `baseCommitId`, equal to the current expected remote branch SHA;
- exact reviewed unidiff SHA-256;
- exact canonical changed-path SHA-256.

Any drift fails closed. An `IN_PROGRESS` session cannot publish.

## Parallelism and collision control

Concurrency is keyed by target branch, not globally. Therefore independent A/B/C branches may publish concurrently, while two publications to the same branch serialize. The provider session itself remains governed by the existing one-writer-per-write-domain rule.

## Publication and idempotency

The workflow first reads the remote branch and requires the exact expected SHA. It applies the exact reviewed patch to that exact SHA, commits with publication identity trailers, and performs a normal non-force push.

After the push, the workflow reads the authoritative remote ref. A push command failure is not blindly retried: if the readback equals the local candidate SHA, the outcome is reconciled as published; otherwise the workflow fails.

A repeated request can resolve `ALREADY_PUBLISHED` only when the current branch head is exactly one commit above the expected base and contains matching Jules-session and review-digest trailers. Any other remote movement is drift and fails closed.

## Performance intent

The publisher intentionally does not rerun the product's full test matrix. Validation belongs to the Jules/Controller review stage and later PR/CI gates. Candidate publication performs only identity, scope, patch-application, Git, and postcondition checks, keeping the transport path short while preserving fail-closed controls.

## Stop gate

`REMOTE_CANDIDATE_SHA_VERIFIED / NO_ACCEPTANCE / NO_MERGE / NO_RELEASE / NO_DEPLOY`
